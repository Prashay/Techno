How to create Thread in application? Define different way of creating it?

Thread can be created in to two ways:

  • extends Thread class
  • implements Runnable interface

Extends Thread class

public class CreatingThread extends Thread{

Implements Runnable interface

public class CreatingThread implements Runnable {
          public void run() {

          }

          }
      }

Define Thread Scheduler?

Thread Scheduler is a component of Java that decides which thread to run or execute and which thread to wait. Every thread have priority of its own ,if there is more than one thread in the runnable state, it is up to the thread scheduler to pick one of the threads and ignore the other ones. There are two factors for scheduling a thread i.e. Priority and Time of arrival.
Priority: Priority of each thread lies between 1 to 10. Default priority of the thread is 5 If a thread has a higher priority, it means that thread has got a better chance of getting picked up by the thread scheduler.

  • public static int MIN_PRIORITY: It is the maximum priority of a thread. value of it is 1.
  • public static int NORM_PRIORITY: It is the normal priority of a thread. value of it is 5.
  • public static int MAX_PRIORITY: It is the minimum priority of a thread. value of it is 10

it can be changed any time after creation. We can check it by getPriority() method or setPriority() method for getting and setting the priority.
Time of Arrival: Suppose two threads of the same priority enter the runnable state, then priority cannot be the factor to pick a thread from these two threads. In such a case, arrival time of thread is considered by the thread scheduler. A thread that arrived first gets the preference over the other threads.

Difference between Preemptive scheduling and Time Slicing?

Preemptive scheduling Time Slicing
Under Preemptive scheduling high priority task executes until it enters the wait or dead states Under Time Slicing mechanism to divide the time into slice until re enter to ready task.

Difference Stage of Thread life Cycle?

Thread life Cycle have different Stage :

  • New
  • Runnable
  • Running
  • Waiting/Block
  • Sleep
  • Dead/Terminate

New: when thread is created ,it is in new state until thread call start() method.
Runnable : After starting thread will be in Runnable state until thread scheduler assign priority.
Running: After thread scheduler select thread for running i.e thread is selected for the execution by thread scheduler
Waiting/Block : State of thread is in waiting or block stage for monitor lock .Thread will be in this stage till notify() or notifyAll() method is called
Sleep : In this state thread is waiting at specific time allocated until timeout completed.
Terminated/Dead : Thread after execution completed will be moved to this state.

Define Deadlock in multithreading?

Deadlock is a situation in which all thread in waiting state are waiting for resource object but non of them get executed .Create universal waiting state and break the code at runtime.

To Avoid Deadlock:
  • use Join() method
  • Avoid the nested lock ()
  • Avoid the circular dependency
  • use Synchronization

Why Wait() ,notify() and notifyAll() present in Object class?

If wait() and notify() were on the Thread instead then each thread would have to know the status of every other thread and there is no way to know thread1 that thread2 was waiting for any resource to access. Hence, notify, wait, notifyAll methods are defined in object class in Java

why Sleep() and Yeild() method are static by nature ?

Sleep() and Yeild() method are static because it work on currently executing thread, rather than any specific thread – you don’t have to specify which thread is currently running to free up the processor.

PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced Concurrency, Threading Models & Hardware (2026) Senior • Tech Lead • 2026

Structured Concurrency (Loom), Scoped Values, StampedLock optimistic reads, AQS internal mechanics, False Sharing, and production thread pool tuning.

Java 21 Loom • Concurrency

1. Structured Concurrency (JEP 453): Eliminating orphan thread leaks and resource hazards.

In traditional unstructured concurrency (using ExecutorService or CompletableFuture), tasks run as independent, disconnected units. If Task A fails or times out, Task B continues running aimlessly in the background, consuming CPU, memory, and database connections.

Structured Concurrency with StructuredTaskScope:
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<User> userSubtask = scope.fork(() -> fetchUser(userId));
    Supplier<Orders> orderSubtask = scope.fork(() -> fetchOrders(userId));

    scope.join();           // Wait for both subtasks concurrently
    scope.throwIfFailed();  // If ANY subtask fails, cancel siblings and rethrow!

    return new DashboardResponse(userSubtask.get(), orderSubtask.get());
}

Tech Lead Advantage: The lexical code block enforces thread lifetime boundaries. If fetchUser() throws an exception, fetchOrders() is immediately cancelled via thread interruption. Stack traces preserve the complete hierarchical parent-child context.

Java 21 Feature • Memory Optimization

2. Scoped Values (JEP 446) vs ThreadLocal: Eliminating memory leaks in Virtual Thread architectures.

ThreadLocal was designed for a world with hundreds of long-lived platform threads. In modern architectures with millions of Virtual Threads, ThreadLocal introduces severe architectural problems:

  • Unbounded Mutability: Any method in a call chain can mutate ThreadLocal.set(), making data flow unpredictable and hard to test.
  • Memory Retention & Leaks: Failing to call remove() keeps references alive indefinitely in thread pool carrier threads.
  • Inheritance Overhead: InheritableThreadLocal copies the entire hash map on thread creation, creating massive memory overhead when spawning 50,000 virtual threads.

Scoped Values Solution: Scoped Values are immutable and strictly bounded to a lexical scope. Child threads inherit scoped values via direct shared pointer references without map copying:

private static final ScopedValue<SecurityContext> CONTEXT = ScopedValue.newInstance();

ScopedValue.where(CONTEXT, userSecurityContext).run(() -> {
    paymentService.process(); // Safely reads CONTEXT.get()
}); // Automatically cleaned up when block exits!
Locking Internals • High Performance

3. StampedLock vs ReentrantReadWriteLock: Optimistic Read Locks & Writer Starvation.

ReentrantReadWriteLock (RRWL) allows multiple concurrent readers, but has two performance drawbacks under heavy load: 1) readers write to a shared internal state counter, causing CPU cache-line bouncing; 2) continuous read traffic can starve writers indefinitely.

The StampedLock Optimistic Read Pattern:
private final StampedLock lock = new StampedLock();
private double x, y;

public double distanceFromOrigin() {
    long stamp = lock.tryOptimisticRead(); // Non-blocking! Acquires NO lock!
    double currentX = x, currentY = y;
    if (!lock.validate(stamp)) { // Check if a writer intervened during read
        stamp = lock.readLock(); // Fallback to pessimistic read lock
        try {
            currentX = x; currentY = y;
        } finally {
            lock.unlockRead(stamp);
        }
    }
    return Math.sqrt(currentX * currentX + currentY * currentY);
}

Trade-off: StampedLock is not reentrant (acquiring the same lock on the same thread causes deadlock) and does not support Condition objects.

AQS • Core Synchronization

4. AQS (AbstractQueuedSynchronizer) Deep Dive: State variable, CLH queue, and LockSupport.

AQS is the backbone of Java's java.util.concurrent synchronizers (ReentrantLock, Semaphore, CountDownLatch, CyclicBarrier):

  • Volatile State: An atomic 32-bit integer (state) manipulated via CAS (compareAndSetState). In ReentrantLock, state = 0 is unlocked; state > 0 represents the reentrancy hold count. In Semaphore, it represents available permits.
  • CLH Waiting Queue: A doubly linked FIFO queue of Node objects. Threads that fail to acquire the lock are enqueued at the tail using CAS.
  • LockSupport.park() & unpark(): Threads wait inside LockSupport.park() (a native OS thread suspension call). When the owner unlocks, it unparks the head node's thread, transferring execution smoothly without busy-waiting CPU spins.
Hardware Concurrency • Low Latency

5. False Sharing and CPU Cache Line Padding: How @Contended prevents cache ping-pong.

Modern CPUs transfer data between main memory and CPU caches in 64-byte chunks called Cache Lines:

  • The Problem: If Thread 1 on Core A modifies variable x and Thread 2 on Core B modifies independent variable y, but both variables happen to reside within the same 64-byte cache line, modifying x invalidates the entire cache line on Core B. The cores waste hundreds of cycles invalidating and reloading data over the interconnect bus (Cache Line Bouncing / False Sharing).
  • The Solution (@Contended): Introduced in JEP 142 and used by LongAdder and the LMAX Disruptor. Injects 128 bytes of padding before and after critical volatile fields, guaranteeing that independent variables occupy distinct hardware cache lines.
Thread Pool Tuning • Production

6. ThreadPoolExecutor Sizing Formula, Queue Sizing, and Rejection Policy Selection.

Sizing thread pools blindly in production leads to either thread starvation or memory exhaustion:

The Goetz Formula:

$N_{\text{threads}} = N_{\text{CPU}} \times U_{\text{CPU}} \times \left(1 + \frac{W}{C}\right)$

where $N_{\text{CPU}}$ is CPU cores, $U_{\text{CPU}}$ is target CPU utilization (0.0 to 1.0), and $\frac{W}{C}$ is the ratio of Wait time (I/O) to Compute time (CPU). For CPU-bound tasks, $N_{\text{threads}} = N_{\text{CPU}} + 1$. For I/O-bound tasks with 90% wait time, sizing is substantially higher.

Rejection Policies:
  • AbortPolicy (Default): Throws RejectedExecutionException. Good for fail-fast APIs.
  • CallerRunsPolicy: Forces the submitting thread (e.g. Tomcat worker) to execute the task directly. Provides automatic backpressure by slowing down incoming request intake!
  • DiscardOldestPolicy: Drops the oldest queued task to make room for newer requests. Useful in real-time telemetry tracking.
