what is Try, Catch and Finally block in Exception Handling in java?

Try: try block is used to defined the exception ,it is definition block which must include with catch and finally .only try block will not executed ,either catch or finally block must be present in the code along with try block.

Catch: catch block is used to handled the exception .it must be included with try block and followed by finally block. for handling multiple exceptions, we may have multiple catch block.

Try without catch block is possible but catch without try is not possible.
When multiple catch block is used then unchecked exception will be handled first and then exception class other wise unreachable catch lock exception occurred.

Finally: finally block is structure of block which execute to check whether exception is handled properly or not.it is independent of the execution of try and catch block. Try without catch but with finally will be possible.

Finally, will not execute only in two situations:
  • When system crashed.
  • When system. exit () method is called.

How to create custom Exception in java?

When we extend exception class then custom checked exception is created whereas when runtime exception class is extended hen custom unchecked exception is created.

Create custom exception :
import java.util.Scanner;
          class IlligalException extends Exception {
              public IlligalException(String s) {
                  super(s);
              }
          }
          public class CustomException {
              public static void validate(int age) throws IlligalException {
                  if (age < 20) {
                      throw new IlligalException("Age is below 19");
                  } else {
                      throw new IlligalException("please ignore");
                  }
              }
              public static void main(String[] args) {
                  Scanner sc = new Scanner(System.in);
                  System.out.println("Enter the age");
                  int age = sc.nextInt();
                  try {
                      validate(age);
                  } catch (Exception e) {
                      System.out.println(e);
                  }
              }
          }

PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced Exception Handling & Distributed Fault Contracts (2026) Senior • Tech Lead • 2026

RFC 7807 Problem Details, asynchronous/reactive error handling, suppressed exceptions, retriable vs fatal failure classification, and distributed trace correlation.

RFC 7807 • Modern API Standards

1. RFC 7807 Problem Details in Spring Boot 3 & Modern Microservices Error Contracts.

In modern REST APIs, returning non-standard JSON error responses (e.g., {"status": "error", "msg": "failed"}) makes cross-service client error parsing brittle. RFC 7807 (Problem Details for HTTP APIs) standardizes error reporting across the industry and is supported natively in Spring Boot 3 via ProblemDetail:

{
  "type": "https://api.technointerview.com/errors/insufficient-balance",
  "title": "Insufficient Account Balance",
  "status": 400,
  "detail": "Account balance of $25.00 is insufficient for transaction of $50.00",
  "instance": "/accounts/acc_12345/transactions",
  "timestamp": "2026-10-12T10:30:00Z",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}

Spring Boot 3 enables this globally with spring.mvc.problemdetails.enabled=true, automatically mapping validation failures (MethodArgumentNotValidException) and framework exceptions to standardized Problem Details.

Async Pipelines • Reactive

2. Exception Handling in Asynchronous & Reactive Pipelines (CompletableFuture & Project Reactor).

Standard try-catch blocks cannot catch exceptions in asynchronous or reactive code because execution occurs on worker threads outside the caller's call stack frame.

CompletableFuture Error Handling:
  • exceptionally(fn): Recovers from errors by returning a fallback value if the stage throws an exception.
  • handle(BiFunction): Receives both the result and throwable, allowing unified handling whether the stage succeeded or failed.
  • whenComplete(BiConsumer): Executes side-effects (e.g. logging/metrics) without altering the downstream result or exception.
Project Reactor / WebFlux:
  • onErrorResume(fallbackPublisher): Switches to a secondary reactive stream on error.
  • retryWhen(Retry.backoff(3, Duration.ofSeconds(1)).jitter(0.5)): Production-grade exponential backoff with randomized jitter to prevent thundering herd problems.
Language Mechanics • AutoCloseable

3. Suppressed Exceptions in Try-With-Resources: Preserving root cause diagnostic traces.

In legacy Java, if a try block threw an exception and the corresponding finally block's close() also threw an exception, the finally exception masked and erased the original business exception!

How Try-With-Resources Solves This:

The original exception thrown inside the try block is preserved as the primary exception. Any secondary exceptions thrown while closing AutoCloseable resources are attached to the primary exception as Suppressed Exceptions:

try (var connection = dataSource.getConnection()) {
    throw new BusinessException("Payment failed");
} catch (Exception ex) {
    // Primary exception is BusinessException
    for (Throwable suppressed : ex.getSuppressed()) {
        log.error("Suppressed resource closure failure: ", suppressed);
    }
}
Resilience • Failure Classification

4. Exception Classification in Distributed Systems: Transient Retriable vs Fatal Domain Errors.

A major cause of cascading failure in microservices is retrying the wrong errors. Microservices must strictly classify exceptions into two categories:

Category Examples Handling Strategy
Transient / Retriable ConnectTimeoutException, SocketTimeoutException, HTTP 503 Service Unavailable, database deadlock Retry with Exponential Backoff + Jitter. Tripped in Circuit Breaker if failure rate persists.
Fatal / Non-Retriable ConstraintViolationException, BadCredentialsException, HTTP 400 Bad Request, HTTP 404 Not Found Fail Immediately (Fast-fail). Must be excluded from Circuit Breaker error counts using ignoreExceptions!
Modern Consensus • Clean Architecture

5. Checked vs Unchecked Exceptions: Why modern Java frameworks abandoned Checked Exceptions.

Java is the only mainstream programming language with checked exceptions (C#, Kotlin, TypeScript, Go, and Python have none). In modern enterprise architecture, checked exceptions are widely considered an anti-pattern:

  • Violation of Open/Closed Principle: Declaring throws SQLException on a repository leaks storage details into business service interfaces. Changing an implementation to MongoDB forces signature changes across 10 layers.
  • Incompatibility with Functional Programming: Java 8+ functional interfaces (Function<T, R>, Consumer<T>, Predicate<T>) do not declare checked exceptions, requiring clumsy try-catch wrappers inside Lambdas.
  • Modern Best Practice: Use unchecked (runtime) exceptions for technical/infrastructure faults, and return explicit Result types or Optional for expected domain alternatives.
Observability • SRE Troubleshooting

6. Correlating Distributed Exceptions using OpenTelemetry, MDC, and Automated Alerts.

When an unhandled exception occurs in production across a chain of 6 microservices, finding the root cause manually through SSH logs is impossible. Senior engineering teams implement Unified Trace Correlation:

  • Automatic MDC Injection: Spring Boot 3 Observation extracts the OpenTelemetry traceId and injects it into SLF4J MDC before any controller or listener executes.
  • Global ControllerAdvice Capture: When an unhandled exception reaches the controller, the exception handler extracts tracer.currentSpan().context().traceId() and includes it in both the log entry and the RFC 7807 response body.
  • Instant Troubleshooting: On-call engineers copy the traceId from customer tickets directly into Grafana Tempo / Jaeger, displaying the exact microservice, class, method, and database query that failed in under 15 seconds.
