Inheritance

Inheritance is mechanism to acquire property and behaviour of parent object to its child .
“extends” keyword is used for implementation of inheritance.
Inheritance represents the IS-A relationship which is also known as a parent-child relationship.

Need of Inheritance

  • For method overriding

To avoid method ambiguity java does not support multiple inheritance. Since, Every child class extend parent property when JVM call parent property ,but it will confused which parent property will be acquired .

Can main method can be overloaded or overridden?

The main method can be overloaded but cannot be overridden in Java. when we overload main method , JVM still run original method ,it will never call our overloaded main method.
overriding is not happening in the case of main method as it is static method which is independent of object creation and overriding is binding of object only

Can we Override private or Static method?

No, we can not override any static method as it belong to class level initialization rather then object level.

PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced OOP, Architecture & System Modeling Senior • Tech Lead • 2026

Composition over inheritance, SOLID in microservices, Diamond problem resolution, synthetic bridge methods, and DDD Value Objects.

Design Principles • Architecture

1. Why do senior architects advocate "Composition over Inheritance"? Explain the Fragile Base Class problem.

While inheritance represents an IS-A relationship, it violates encapsulation because subclasses depend on the internal implementation details of the parent class (tight coupling).

The Fragile Base Class Problem:

Consider a subclass CustomCountingSet inheriting from HashSet that overrides add() and addAll() to count inserted items. If the superclass's addAll() internally calls add(), every item gets counted twice! A benign internal refactor in the parent library silently breaks subclass invariants.

The Composition Solution: Use composition and interface forwarding (Delegator/Decorator pattern). Wrap the instance in a private field and delegate calls cleanly. This allows replacing behavior at runtime, enforces clear boundaries, and prevents unwanted methods from leaking into the public API.

SOLID in Distributed Systems

2. How do the SOLID principles apply to modern Microservices and Distributed Architecture?

  • Single Responsibility Principle (SRP): A microservice should map to a single Domain-Driven Design (DDD) Bounded Context. If an order service also handles invoice PDF generation and SMS sending, it violates distributed SRP.
  • Open/Closed Principle (OCP): APIs and event schemas must be open for extension, closed for modification. Use protobuf/Avro schema registries with backward-compatible field additions; never introduce breaking REST payload changes without URL/header versioning.
  • Liskov Substitution Principle (LSP): Microservice contract testing (Pact / Spring Cloud Contract). Any replacement service or provider version must fulfill consumer contracts without altering business preconditions or postconditions.
  • Interface Segregation Principle (ISP): Instead of giant monolithic REST endpoints returning 50-field JSON payloads, provide granular, client-specific BFF endpoints or GraphQL schemas tailored strictly to client needs.
  • Dependency Inversion Principle (DIP): Hexagonal Architecture (Ports and Adapters). Core business domain logic must never depend directly on databases, Kafka, or third-party SDKs; it defines interfaces (Ports) that infrastructure adapters implement.
Language Internals • Diamond Problem

3. How does Java resolve the Diamond Problem with multiple interface default methods?

Since Java 8 introduced default methods in interfaces, a class can inherit conflicting method implementations from multiple interfaces. The Java compiler resolves conflicts using 3 strict rules:

  1. 1. Classes beat Interfaces: A method declaration in a superclass or abstract class always takes precedence over any default method in an interface.
  2. 2. Sub-interfaces beat Super-interfaces: If interface B extends interface A and both provide a default method, B's method takes precedence (most specific wins).
  3. 3. Explicit Disambiguation: If two unrelated interfaces (e.g. InterfaceA and InterfaceB) declare identical default method signatures, the compiler throws a compile-time error: "class inherits unrelated defaults". The developer must override the method explicitly: 
    public void print() {
    InterfaceA.super.print(); // Explicit disambiguation
}
JVM Bytecode • Covariant Returns

4. What are Covariant Return Types, and why does the JVM compiler generate synthetic Bridge Methods?

Covariant Return: When an overriding method in a child class returns a narrower subtype of the type declared in the parent class:

class Producer { public Number get() { return 1; } }
class IntegerProducer extends Producer { @Override public Integer get() { return 1; } }

Synthetic Bridge Methods: In Java bytecode, method descriptors include the return type (()Ljava/lang/Number; vs ()Ljava/lang/Integer;). To maintain polymorphic binary compatibility with callers compiled against the superclass, the Java compiler automatically synthesizes a hidden bridge method with the superclass signature that delegates to the specialized child method:

// Generated by compiler:
public synthetic bridge Number get() {
    return this.get(); // calls Integer get()
}
Domain-Driven Design • Value Objects

5. Entities vs Value Objects in DDD: Designing immutable Domain Value Objects with Java Records.

In Domain-Driven Design (DDD), clean domain separation between Entities and Value Objects prevents bugs and race conditions:

Characteristic Domain Entity Domain Value Object
Identity Has unique identity (UUID / ID) that persists across state mutations No identity; defined entirely by the combination of its attributes
Mutability State transitions over time (e.g. Order: PENDING → SHIPPED) Strictly Immutable; replacing a value means creating a new instance
Equality Based on ID equality (e1.id == e2.id) Based on structural attribute equality (Money(10, "USD") == Money(10, "USD"))

Implementation with Java Records: Use compact constructors to enforce invariant validation upfront:

public record Money(BigDecimal amount, Currency currency) {
    public Money { // Compact constructor
        Objects.requireNonNull(currency, "Currency cannot be null");
        if (amount == null || amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("Amount cannot be negative");
        }
    }
}
Architecture Metrics • Coupling

6. As a Tech Lead, how do you measure and govern Loose Coupling and High Cohesion? (Afferent vs Efferent Metrics).

Architectural modularity is measured mathematically using Robert C. Martin's Package Coupling Metrics:

  • Afferent Coupling ($C_a$): Number of classes/modules outside this package that depend on classes inside it (incoming dependencies / responsibility).
  • Efferent Coupling ($C_e$): Number of classes inside this package that depend on classes outside it (outgoing dependencies).
  • Instability ($I$): Calculated as $I = \frac{C_e}{C_a + C_e}$. A value of $I = 0$ means maximally stable (core domain / shared libraries); $I = 1$ means maximally volatile (UI / controllers).
  • Stable Abstractions Principle: Highly stable packages ($I \approx 0$) must be abstract (interfaces), so they can be extended without requiring frequent re-compilations. Tools like ArchUnit automate these architecture rules in CI/CD pipelines.
