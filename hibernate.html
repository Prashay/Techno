What are the hibernate annotations present?

  • @Entity
  • @ID
  • @Table
  • @Column
  • @Generated value
  • @Transient
  • @One to one
  • @one to many

    • @Entity : this annotation is used in model class or entity class to define the base property or to identify the entity class.

    @ID : this annotation is used to identify primary key value in the class independent of table defined or not , it is variable level annotation. used for id

    @Table : when we already defined the table then this annotation is used to update table name manually ,if @table is not defined in the entity class hibernate create table automatically with same name as entity class.

    @Column : when we already defined the table then this annotation is used to update Column name manually ,if @column is not defined in the entity class hibernate create table automatically with same name as entity class.

    @GeneratedValue : it is used to define how generate the value for particular column ex: @GeneratedValue(strategy = GenerationType.IDENTITY) for auto_increament value we can use it

    @Transient : This annotation denotes that such field is not mandatory to save in db or we can ignore such feilds .this is part of javax.persistence package. (Let’s say you have created two variables in an entity class in one you want to save in database and second is derived from the first one. So we need not save the second field in the database and can be map with @Transient annotation, the second field will be ignored to save in data base.)

    @One to One : this annotation is used to show one to one relation between one object to the other object such as student and address

    @One to many : this annotation is used to show one to many relation between one object to the other objects such as student and phone.

PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced Hibernate, Caching & Performance Engineering (2026) Senior • Tech Lead • 2026

N+1 query solutions, Second-Level caching with Redis, Optimistic vs Pessimistic locking, Hibernate 6 SQM architecture, batching, and @Transactional pitfalls.

Performance • Query Optimization

1. Solving the N+1 Select Problem: JOIN FETCH vs JPA EntityGraph vs @BatchSize.

The N+1 Query Problem occurs when loading 1 parent entity query triggers $N$ additional sub-queries to fetch lazy child associations (e.g., 100 orders trigger 100 separate queries for customer details).

Strategy Mechanism Pros Cons & Pitfalls
JOIN FETCH Generates a single SQL query using an inner/left join in JPQL Single database roundtrip Cannot fetch multiple List collections simultaneously (Cartesian Product / MultipleBagFetchException)
JPA @EntityGraph Declarative graph of attributes to fetch eagerly at runtime Dynamic: can use different fetch plans for different repository methods Same Cartesian product limitation if multiple subgraphs are eagerly fetched
@BatchSize(size=50) Executes sub-queries using WHERE id IN (?, ?, ...) Safely handles multiple collections without Cartesian explosion Requires multiple SQL statements (1 parent query + $\lceil N/50 \rceil$ batch queries)
Caching Architecture • Second-Level

2. Hibernate Multi-Level Caching: First-Level, Second-Level (Redis/Hazelcast), and Query Cache.

  • First-Level Cache (Session Cache): Mandatory and tied to the lifecycle of the current EntityManager / Session. Acts as an Identity Map and dirty-checking buffer. Automatically discarded when transaction ends.
  • Second-Level Cache (SessionFactory Cache): Shared across all sessions and application nodes (using Redis via Redisson, or Hazelcast). Stores dehydrated entity state (arrays of primitive values, not managed entity objects).
  • Query Cache: Stores query parameter hashes mapping to entity primary keys (IDs). Production Warning: Any insert, update, or delete on the target table invalidates the entire query cache region! Only use for read-heavy, almost static tables.
Concurrency • Data Integrity

3. Optimistic Locking (@Version) vs Pessimistic Locking (PESSIMISTIC_WRITE) in Financial Workflows.

When multiple concurrent transactions update the same entity (e.g. deducting account balance or purchasing warehouse stock), concurrency control is mandatory:

  • Optimistic Locking (@Version): Adds an integer/timestamp column. Updates execute: UPDATE account SET balance = ?, version = version + 1 WHERE id = ? AND version = ?. If another transaction updated the row first, 0 rows are affected and Hibernate throws OptimisticLockException.
    Best for: High-concurrency reads with low conflict rates; clients retry on failure.
  • Pessimistic Locking (LockModeType.PESSIMISTIC_WRITE): Issues a database-level row lock: SELECT ... FOR UPDATE. All other transactions reading or writing the row block until the transaction commits.
    Best for: High-contention financial transactions where retries are too expensive. Must use lock timeouts (e.g. javax.persistence.lock.timeout = 3000) to prevent distributed database deadlocks.
Spring Boot 3 • Hibernate 6.x

4. Hibernate 6.x Architectural Evolution: Semantic Query Model (SQM) & Performance Boosts.

Hibernate 6 (the foundation of Spring Boot 3 / Spring Data JPA 3) represents the biggest internal rewrite in Hibernate history:

  • Semantic Query Model (SQM): Completely replaced the ancient ANTLR 2 HQL parser. HQL and Criteria queries now compile to a single unified semantic tree (SQM), allowing identical optimizations and native SQL tree translation.
  • Direct JDBC Read/Write: Bypasses legacy reflection and object array boxing during result set hydration. Queries read typed columns directly from JDBC ResultSet, boosting query execution performance by 15-30%.
  • Native JSON and Array Types: Native support for PostgreSQL/MySQL JSON and Array columns via @JdbcTypeCode(SqlTypes.JSON) without needing external third-party Hibernate Types libraries.
High Volume • Batch Processing

5. Processing 500,000 Records Without OutOfMemoryError: JDBC Batching vs StatelessSession.

Inserting or updating 500,000 records using standard repository.save() crashes the JVM with OutOfMemoryError because Hibernate's First-Level Cache retains every entity in memory for dirty checking.

Production Strategies:
  • Strategy A: Flush & Clear in Batches: 
    for (int i = 0; i < items.size(); i++) {
    entityManager.persist(items.get(i));
    if (i % 50 == 0) {
        entityManager.flush(); // Sends JDBC batch to database
        entityManager.clear(); // Empties first-level cache to reclaim heap!
    }
}
    Enable in application.properties: spring.jpa.properties.hibernate.jdbc.batch_size=50 and spring.jpa.properties.hibernate.order_inserts=true.
  • Strategy B: Hibernate StatelessSession: A lightweight, command-oriented session that bypasses the First-Level Cache, dirty-checking, cascades, and interceptors completely. Streams raw JDBC operations directly with near-zero heap overhead.
Transactions • Common Traps

6. Subtle Traps of @Transactional: Self-invocation, Checked Exception rollbacks, and Connection Pool exhaustion.

  • Self-Invocation Proxy Bypass: Spring manages @Transactional via CGLIB dynamic proxies. Calling a @Transactional method from another method within the same class calls this.method() directly, bypassing the Spring proxy! Transaction boundaries are ignored and no transaction is opened.
  • Checked Exception Rollback Defaults: By default, Spring rolls back transactions only on RuntimeException and Error! If a method throws a checked exception (e.g. IOException, SQLException), Spring commits the transaction! Fix: always specify @Transactional(rollbackFor = Exception.class).
  • Propagation.REQUIRES_NEW Pool Exhaustion: When a method with REQUIRES_NEW is called from an existing transaction, Spring suspends the first transaction (holding its database connection) and borrows a second database connection from HikariCP. Under high concurrent load, this causes mutual connection starvation and application deadlock.
