Method reference used to refer to the method of functional interface.
It can be used to replace Lambda Expression while referring to a method.

Lembda Expression Equivalent Method Reference
(String s)->integer.parseInt integer::parseInt
(String s)->s.toLowerCase String::toLowerCase
(int i)->System.out.println(i) System.out::println
(Student s)->s.getName(); Student::getName
()->s.getName() s::getName
()->new Student() Student::name 
import java.util.function.Function;

                public class Java8MethodReferences {
                    public static void main(String[] args) {
                        //Calling parseInt() method using lambda
                
                        Function < String, Integer > lambdaFunction = (String s) - > Integer.parseInt(s);
                        System.out.println(lambdaFunction.apply("12"));
                
                        //Calling parseInt() method using method reference

                        System.out.println(referenceFunction.apply("12"));
                    }
                }
PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced Functional Java, Streams Internals & Asynchronous Pipelines (2026) Senior • Tech Lead • 2026

Stream Spliterators and Sink pipeline execution, ForkJoin common pool hazards, Collectors.teeing, invokedynamic bytecode, and CompletableFuture pipelines.

Streams Internals • Pipeline Execution

1. Java Streams Internals: Spliterators, Sink chains, Loop Fusion, and Lazy Evaluation.

Java Streams do NOT store data. A Stream is an on-demand computational pipeline that executes via Loop Fusion:

  • Sink Pipeline Stages: Intermediate operations (filter(), map(), sorted()) create a doubly-linked list of Sink objects wrapping each other.
  • Lazy Evaluation: No data processing occurs when intermediate operations are declared. Processing begins only when a terminal operation (e.g. collect(), findFirst(), count()) is invoked.
  • Loop Fusion: Instead of making multiple passes over the collection (one pass for filter, one for map), elements are pushed through the entire Sink chain one element at a time in a single pass.
  • Spliterator: The parallel engine of streams. Provides trySplit() to partition data chunks recursively across worker threads, and characteristics() (e.g. ORDERED, SIZED, DISTINCT) to skip redundant operations (e.g., skipping sort if source is already sorted).
Concurrency Hazards • ForkJoinPool

2. Why using parallelStream() in Enterprise Web Services is dangerous: CommonPool Starvation.

Calling list.parallelStream() executes tasks on the shared, JVM-wide ForkJoinPool.commonPool(), which has a thread count equal to CPU cores minus 1.

The Production Starvation Trap:

If an HTTP request thread triggers a parallel stream that executes blocking I/O (e.g., calling an external REST API or database), those worker threads block inside the common pool. Because the common pool is JVM-wide, this starvates unrelated parallel streams across the entire application, causing widespread request timeouts and latency spikes.

Senior Engineer Rule: Reserve parallelStream() strictly for CPU-intensive, in-memory computations. For concurrent I/O operations, use Java 21 Virtual Threads or dedicated ExecutorService instances.

Advanced Collectors • Modern Java

3. Advanced Collectors: Collectors.teeing(), multi-level groupingBy(), and downstream aggregation.

Introduced in Java 12, Collectors.teeing() merges the results of two independent downstream collectors in a single pass over the stream:

record Summary(double average, long totalCount) {}

Summary summary = transactions.stream()
    .collect(Collectors.teeing(
        Collectors.averagingDouble(Transaction::amount),
        Collectors.counting(),
        Summary::new // Merges the two results together in 1 pass!
    ));

Multi-Level Grouping: Grouping employees by department and calculating the highest salary in each department using downstream reduction:

Map<Department, Optional<Employee>> topEarners = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::department,
        Collectors.maxBy(Comparator.comparing(Employee::salary))
    ));
JVM Bytecode • invokedynamic

4. Lambdas vs Anonymous Inner Classes at the Bytecode Level: invokedynamic & LambdaMetafactory.

Lambda expressions are NOT syntax sugar for Anonymous Inner Classes. The architectural differences at runtime and bytecode level are significant:

Feature Anonymous Inner Class Lambda Expression
Generated Class Files Generates a separate disk class file (MyClass .class) for every occurrence Zero extra class files generated on disk
Bytecode Instruction Compiles to new MyClass () + invokespecial Compiles to an invokedynamic (indy) instruction
Memory Allocation Allocates a new object on heap on every invocation unless manually cached Translates to a private method via LambdaMetafactory; non-capturing lambdas are cached as singletons!
this Scope Refers to the inner class instance Refers to the enclosing outer class instance
Clean Code • Anti-Patterns

5. java.util.Optional: Production Best Practices & High-Frequency Anti-Patterns.

  • Intended Purpose: Optional was designed strictly as a method return type to indicate that a result might be absent without returning null.
  • Anti-Pattern 1: Optional as Field or Parameter: Optional is NOT Serializable. Using it as a class field breaks serialization frameworks (Jackson, Java serialization) and adds an extra 16-24 byte pointer overhead on the heap.
  • Anti-Pattern 2: Optional.get() without isPresent(): Defeats the purpose of Optional and throws NoSuchElementException. Use orElseThrow() with descriptive custom exceptions or map().orElse().
  • Anti-Pattern 3: orElse() vs orElseGet(): orElse(expensiveCalculation()) executes the fallback method every time, even if the Optional contains a value! Always use orElseGet(() -> expensiveCalculation()) to defer evaluation lazily.
Asynchronous Composition • Futures

6. Complex CompletableFuture Orchestration: Chaining, Timeouts, and Error Recovery.

Senior engineers construct non-blocking asynchronous pipelines using monadic composition:

CompletableFuture<OrderSummary> pipeline = CompletableFuture
    .supplyAsync(() -> orderClient.getOrder(orderId), customExecutor)
    .thenCompose(order -> 
        CompletableFuture.supplyAsync(() -> inventoryClient.reserve(order))
            .thenCombine(
                CompletableFuture.supplyAsync(() -> paymentClient.charge(order)),
                (inv, pay) -> new OrderSummary(order, inv, pay)
            )
    )
    .orTimeout(3, TimeUnit.SECONDS) // Java 9+ timeout support!
    .exceptionallyCompose(ex -> {
        log.error("Pipeline failed: {}", ex.getMessage());
        return CompletableFuture.completedFuture(OrderSummary.failed(orderId));
    });

Key Insight: thenApply is for synchronous value transformation ($T \to U$), while thenCompose is monadic flatMap ($T \to \text{CompletableFuture}\langle U\rangle$), preventing nested CompletableFuture<CompletableFuture<T>> types.
