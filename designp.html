Singleton Design Pattern

The Singleton pattern is a design pattern that make sure Class has only one
instance and provides a global point of access to that instance.

key Feature of Singleton pattern:

  • Singleton pattern uses a private constructor and
    a static method to ensure one single instance throughout the class
  • it provide global access by get instance method
  • Singleton pattern control access to share across the system such as db connection
    or object configuration
  • it is used to implementation caching ,logging.

Singleton Class

Public class Singleton {
            private static Singleton instance;
            //private constructor
            private Singleton() {}
            public static Singleton getInstance() {
                if (instance == null) {
                    instance = new Singleton();
                }
                return instance;
            }
        
            public void Show() {
                System.out.println("verify Singleton");
            }
        }

Here are the main points of Above code :

  • Singleton class have private constructor ,which prevent it from being
    instantialized from outside the class
  • The getInstance() method is public static method that return only one
    instance of Singleton class.
  • the instance variable is private and static that means it is accessible
    with getInstance() method only.
  • if instance is null it will create new instance of sinleton otherwise return the instance it self
Public class Singleton main() {
            public static void main(String[] args) {
                Singleton object = Singleton.getInstance();
                object.show(); //it will print value of show method with single instance
            }
        }

Factory Design Pattern

The factory pattern is design pattern that provides a way to create objects
without specifying the exact class of object that will be created.

key Feature of Factory Pattern :

  • it is independent of exact class ,so code is more flexible and easier to change.
  • it allows the encapsulation
  • make the code reusable
package factoryPattern;


            interface Ivechile {
                void drive();
            }
            
            class Car implements Ivechile {
                public void drive() {
                    System.out.println("Driving a Car");
                }
            }
            class Truck implements Ivechile {
                public void drive() {
                    System.out.println("Driving a Truck");
                }
            }
            class Bus implements Ivechile {
                public void drive() {
                    System.out.println("Driving a Bus");
                }
            }
            
            class VechileFactory {
                public Ivechile getIvechile(String vechileType) {
                    if (vechileType.equalsIgnoreCase("car")) {
                        return new Car();
                    } else if (vechileType.equalsIgnoreCase("bus")) {
                        return new Bus();
                    } else if (vechileType.equalsIgnoreCase("truck")) {
                        return new Bus();
                    } else {
                        return null;
                    }
                }
            }
            public class VechileFactoryMain {
                public static void main(String[] args) {
                    VechileFactory vc = new VechileFactory();
                    Ivechile vci = vc.getIvechile("car");
                    vci.drive();
                    Ivechile vci1 = vc.getIvechile("bus");
                    vci1.drive();
                    Ivechile vci2 = vc.getIvechile("truck");
                    vci2.drive();
            
                }
            }

Cloud-Native • Event Sourcing

1. CQRS (Command Query Responsibility Segregation) & Event Sourcing Architecture.

In high-scale enterprise systems, traditional CRUD models where the same relational schema handles both complex business writes and reporting queries suffer from contention, indexing trade-offs, and lock saturation.

CQRS + Event Sourcing Architecture:
  • Command Model (Write Side): Optimized for business logic invariants. Validates domain rules and appends immutable events (e.g. OrderCreatedEvent, ItemAddedEvent) to an append-only Event Store. Current state is never overwritten; it is reconstructed by replaying events.
  • Query Model (Read Side): Asynchronous event projectors consume events from the Event Store and populate denormalized, purpose-built read databases (e.g., Elasticsearch for text search, Redis for key-value lookups, PostgreSQL for relational views).
  • Trade-offs: Introduces Eventual Consistency (read models reflect writes with slight millisecond replication lag), event schema evolution challenges (upcasting), and snapshotting requirements for entities with thousands of events.
Resiliency Patterns • Stability

2. Defense-in-Depth Resiliency: Circuit Breaker, Bulkhead, Rate Limiter, and Retry Patterns.

Cascading failures in distributed systems happen when a slow or failing downstream dependency causes upstream callers to wait, exhausting threads and toppling the entire platform. Senior architects combine 4 orthogonal patterns:

Pattern Failure Mode Addressed Core Mechanism
Circuit Breaker Persistent downstream outage or high error rate Fails fast immediately (State: OPEN) to protect downstream and preserve caller latency
Bulkhead Slow downstream service consuming all server threads Isolates thread pools or semaphores so Service A failure cannot exhaust threads needed for Service B
Rate Limiter Traffic spikes, noisy neighbors, and DDoS attacks Enforces maximum calls per time window, rejecting excess traffic with HTTP 429
Retry with Backoff Transient network glitches and momentary blips Retries failed requests using exponential backoff with randomized jitter to prevent thundering herds
Spring Boot Design • Clean Code

3. Modern Strategy & Factory Patterns via Spring Boot Dynamic Dependency Injection.

Senior Java developers eliminate brittle switch-case statements and if-else chains by leveraging Spring's built-in container injection:

public interface PaymentStrategy {
    PaymentType getType();
    PaymentResponse pay(PaymentRequest request);
}

@Service
public class PaymentFactory {
    private final Map<PaymentType, PaymentStrategy> strategyMap;

    // Spring automatically injects ALL beans implementing PaymentStrategy!
    public PaymentFactory(List<PaymentStrategy> strategies) {
        this.strategyMap = strategies.stream()
            .collect(Collectors.toMap(PaymentStrategy::getType, Function.identity()));
    }

    public PaymentStrategy getStrategy(PaymentType type) {
        return Optional.ofNullable(strategyMap.get(type))
            .orElseThrow(() -> new UnsupportedOperationException("No strategy for: " + type));
    }
}

Adding a new payment provider (e.g. ApplePay) requires creating a new @Component implementing PaymentStrategy. Zero modifications to existing classes (Pure Open/Closed Principle).

Kubernetes Patterns • Mesh

4. Cloud-Native Pod Patterns: Sidecar, Ambassador, and Adapter Patterns in Kubernetes.

In containerized Kubernetes environments, multi-container pods implement three classic structural patterns:

  • Sidecar Pattern: Extends or enhances the main application container without modifying application source code. Example: Envoy proxy sidecar in Istio injecting mutual TLS (mTLS), Prometheus metric scraping, and distributed tracing headers.
  • Ambassador Pattern: Acts as a local proxy that abstracts connections to external services. The application talks to localhost:6379; the ambassador proxy handles sharding, failover, and routing to remote Redis clusters.
  • Adapter Pattern: Standardizes heterogeneous application interfaces. Example: an adapter container that reads proprietary log formats or metrics from the primary application container and exposes them in Prometheus standard format.
Reliable Messaging • Kafka

5. Transactional Outbox Pattern & Idempotent Consumer Pattern in Event-Driven Architecture.

Asynchronous microservice communication requires guaranteed delivery and processing without duplicates:

  • The Outbox Pattern: Eliminates the dual-write bug when saving to database and publishing to Apache Kafka. The event is persisted into an outbox database table inside the same local ACID transaction. A Debezium CDC pipeline tails the transaction log to stream messages to Kafka.
  • The Idempotent Consumer Pattern: Because network partitions cause brokers to deliver messages more than once (At-Least-Once delivery), consumers must be strictly idempotent:
    1. Unique message ID check against an idempotency_keys table.
    2. Conditional database updates (e.g. UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'PENDING').
    3. Natural idempotency: setting a state rather than incrementing a balance.
Legacy Migration • Zero Downtime

6. The Strangler Fig Pattern: Incrementally Migrating Monoliths to Microservices Without Big-Bang Risk.

Big-Bang rewrites of multi-million-line legacy systems fail over 80% of the time. The Strangler Fig Pattern (inspired by the Australian strangler fig tree that envelops and replaces its host tree) migrates systems iteratively over 12-24 months:

  1. Phase 1 (Interception): Place an API Gateway (Envoy/Kong) in front of the legacy monolith. All user traffic flows through the gateway to the monolith unchanged.
  2. Phase 2 (Carve Out): Select a discrete business domain (e.g., Notification or Inventory). Build a modern microservice implementing this domain.
  3. Phase 3 (Data Synchronization): Use CDC (Change Data Capture) or dual-writing to synchronize data bi-directionally between monolith and microservice databases.
  4. Phase 4 (Traffic Shift): Route 5% → 50% → 100% of the target API path (e.g. /api/notifications/*) to the new microservice via the Gateway.
  5. Phase 5 (Decommission): Once verified in production, delete the legacy code from the monolith. Repeat for the next domain until the monolith disappears.
