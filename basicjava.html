Can a Constructor be private?

Yes, we can declare a constructor as private. If we declare a constructor as private we are not able to create an object of a class.We can use this private constructor in the Singleton Design Pattern

Conditions for Private Constructor

  • A private constructor does not allow a class to be sub classed.
  • A private constructor does not allow to create an object outside the class.
  • If all the constant methods are there in our class we can use a private constructor.
  • If all the methods are static then we can use a private constructor.
  • If we try to extend a class which is having private constructor compile time error will occur.

What is Serialization in java? how to make any class serializable in java

Serialization in Java is a mechanism of writing the state of an object into a byte-stream. For serializing the object, we call the writeObject() method of ObjectOutputStream class, and for deserialization we call the readObject() method of ObjectInputStream class. Serializable is a marker interface (has no data member and method). It is used to “mark” Java classes so that the objects of these classes may get a certain capability. The Cloneable and Remote are also marker interfaces

How to make any class immutable in java?

To make any immutable we have to perform following steps:

  • Define the class final so that none of class extend its property.
  • Define the variable as private so that no further initialization.
  • Define all mutable field private
  • Do not define setter method only define getter method no one set new value.
  • All the initialization through constructor
  • Perform the object cloning.

What is object cloning in java ?

The object cloning is a way to create exact copy of an object. The clone() method of Object class is used to clone an object.
The java.lang.Cloneable interface must be implemented by the class whose object clone we want to create. If we don’t implement Cloneable interface, clone() method generates CloneNotSupportedException.

protected Object clone() throws CloneNotSupportedException

Example :

class Student18 implements Cloneable {
          int rollno;
          String name;
      
          Student18(int rollno, String name) {
              this.rollno = rollno;
              this.name = name;
          }
      
          public Object clone() throws CloneNotSupportedException {
              return super.clone();
          }
      
          public static void main(String args[]) {
              try {
                  Student18 s1 = new Student18(101, "amit");
      
                  Student18 s2 = (Student18) s1.clone();
      
                  System.out.println(s1.rollno + " " + s1.name);
                  System.out.println(s2.rollno + " " + s2.name);
      
              } catch (CloneNotSupportedException c) {}
      
          }
      }

PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced Java Core & JVM Internals (2026) Senior • Tech Lead • 2026

Virtual threads vs platform threads, Java Memory Model (JMM), modern Algebraic Data Types, Generational ZGC, and Metaspace classloader dynamics.

JVM Internals • Java 21 Loom

1. Java 21 Virtual Threads vs Platform Threads: Deep dive into heap memory, stack frames, and scheduling.

Virtual Threads (Project Loom, Java 21) revolutionize Java concurrency by decoupling user-mode threads from operating system kernel threads:

Feature OS Platform Thread Virtual Thread (Java 21+)
Memory Footprint ~1MB to 2MB fixed OS stack memory ~few hundred bytes initially; dynamically grows on JVM heap
Creation Cost Expensive system call to OS kernel Cheap Java object allocation on heap ($O(1)$)
Thread Capacity Few thousands max before crashing with OutOfMemoryError Millions of concurrent threads
Scheduling Preemptive OS kernel scheduler Cooperative user-mode scheduler running on a ForkJoinPool carrier pool
Blocking I/O Blocks OS kernel thread in waiting state Unmounts virtual thread from carrier thread; carrier runs other tasks

When NOT to use Virtual Threads: CPU-bound tasks (cryptographic hashing, video transcoding, in-memory ML matrix operations). Virtual threads do not make CPU calculations faster; they only scale I/O-bound concurrency.

Memory Model • Concurrency

2. Explain the Java Memory Model (JMM), the Happens-Before relationship, and hardware cache coherency.

Modern multi-core CPUs maintain L1/L2/L3 hardware caches. Without memory synchronization, writes to a variable by CPU Core 1 reside in its local store buffer/cache and may never be seen by Core 2.

  • The volatile Keyword: Instructs the compiler and CPU to generate Memory Barriers (LoadLoad, StoreStore, StoreLoad). Ensures that all reads read directly from main memory and writes flush immediately to main memory.
  • Instruction Reordering: Compilers and CPU out-of-order execution engines reorder instructions for performance. volatile forbids reordering across the memory barrier.
  • Happens-Before Rules:
    1. Program Order Rule: Each action in a thread happens-before every subsequent action in that thread.
    2. Volatile Variable Rule: A write to a volatile field happens-before every subsequent read of that same field.
    3. Monitor Lock Rule: An unlock on a monitor happens-before every subsequent lock on the same monitor.
    4. Transitivity Rule: If A happens-before B, and B happens-before C, then A happens-before C.
Language Evolution • Java 17-21

3. How do Records, Sealed Classes, and Pattern Matching enable Algebraic Data Types (ADT) in modern Java?

Modern Java allows developers to build robust, compiler-enforced domain models using Algebraic Data Types:

public sealed interface PaymentMethod permits CreditCard, Upi, BankTransfer {}

public record CreditCard(String cardNumber, String cvv, YearMonth expiry) implements PaymentMethod {}
public record Upi(String vpa) implements PaymentMethod {}
public record BankTransfer(String accountNumber, String ifsc) implements PaymentMethod {}

public String processPayment(PaymentMethod method) {
    return switch (method) {
        case CreditCard c -> "Charging CC ending in " + c.cardNumber().substring(12);
        case Upi u        -> "Sending UPI collect request to " + u.vpa();
        case BankTransfer b -> "Initiating NEFT transfer to " + b.accountNumber();
    }; // NO 'default' branch needed! Compiler guarantees exhaustiveness!
}

If a new payment type is added to the sealed interface, the compiler immediately flags errors on all unhandled switch expressions across the entire codebase!

Garbage Collection • Performance

4. Modern Garbage Collectors: G1GC vs Generational ZGC vs Shenandoah on multi-terabyte heaps.

In high-scale enterprise Java, choosing and tuning the Garbage Collector is critical for meeting P99 latency Service Level Objectives (SLOs):

Metric G1GC (Default) Generational ZGC (Java 21+) Shenandoah GC
Pause Times 10ms - 200ms (configurable target) Sub-millisecond (< 1ms) guaranteed < 10ms
Heap Size Range 4GB - 64GB 16MB up to 16 Terabytes 4GB - 100GB+
Core Mechanism Region-based, incremental, Stop-The-World copying pauses Colored Pointers + Load Barriers; concurrent marking, evacuation & relocation Brooks Pointers / Load-Reference Barriers
Generational Support Yes (Young vs Old regions) Yes in Java 21+ (JEP 439): massive throughput boost over ZGC single-gen Generational Shenandoah (Java 21 experimental)
Memory Management • String Internals

5. How does the JVM optimize String memory via Compact Strings, and what are the dangers of String.intern()?

  • Compact Strings (Java 9+): Strings historically stored char[] (2 bytes per character). Compact Strings store byte[] + a coder byte flag. If all characters fit into ISO-8859-1 (Latin-1), only 1 byte per character is allocated, slashing heap consumption by ~45% in typical web applications.
  • G1 String Deduplication: G1 GC identifies distinct String objects that share identical character arrays and points them to the same underlying byte[] without changing object identity. Enabled via -XX:+UseStringDeduplication.
  • Dangers of String.intern(): The String Pool is a native JVM hash table located in native memory. Calling intern() on user-supplied strings (e.g., incoming request IDs or tokens) causes severe hash collision bucket degradation, Metaspace/native memory bloat, and Stop-The-World GC latency spikes. Never intern unbounded dynamic input!
ClassLoading • Metaspace Leakage

6. Explain the ClassLoader Delegation Hierarchy and how custom ClassLoaders cause Metaspace OutOfMemoryError.

Delegation Hierarchy: Bootstrap ClassLoader (C++ native JVM core) → Platform/Extension ClassLoader → Application (System) ClassLoader → Custom / WebApp ClassLoader. Class loading follows parent-first delegation.

The Hot-Deploy Metaspace Memory Leak:

A loaded class can only be garbage-collected if its ClassLoader is garbage-collected. A ClassLoader can only be garbage-collected if:

  1. No instances of any class loaded by that ClassLoader exist.
  2. No static references point to those classes.
  3. No threads are currently executing code loaded by that ClassLoader.

If an application registers a ThreadLocal, an unclosed JDBC driver, or a static logger that retains an object reference during undeployment, the entire WebAppClassLoader and hundreds of metadata classes remain pinned in memory, leading inevitably to java.lang.OutOfMemoryError: Metaspace after 3-4 hot reloads.
