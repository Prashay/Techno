05 • 15 Production Scenarios Performance and capacity

Your API suddenly takes 5 seconds instead of 200 ms. How would you find the bottleneck?

Suggested Spoken Answer (45–60s)

I would first confirm the scope of the regression: which endpoints, when it started, and whether p95 and p99 rose along with traffic or error rates. I'd examine Grafana dashboards for application, database, cache, JVM, and downstream-service metrics. Then I'd use a distributed trace or targeted timings to divide total request time into connection wait, application logic, SQL, Redis, and external calls. I'd check deployment changes, thread saturation, GC pauses, and slow queries. After isolating the dominant delay, I'd fix it and verify the improvement under representative load.

WHAT TO CHECK / EXPLAIN:
  • Compare p50/p95/p99, traffic, error rate, releases, and individual endpoints.
  • Trace each dependency; check DB pool wait, slow SQL, Redis hit rate, outbound HTTP, GC and thread dumps.
  • Validate the fix with load testing and production monitoring; avoid guessing the cause.
YOUR RESUME CONNECTION

Lowe's: you actually improved inventory/lookup API p99 from 8 seconds to 170 ms using distributed Redis caching. Do not imply this exact 5-second incident happened.

FOLLOW-UP What if SQL is fast but p99 is high?
Check queueing, connection acquisition, slow dependency calls, and JVM pauses.
Q47
05 • 15 Production Scenarios Performance and capacity

Your DB connection pool is exhausted. What would you check first?

Suggested Spoken Answer (45–60s)

I'd start with HikariCP metrics for active, idle, pending, and maximum connections, especially acquisition wait time. Then I'd look for long-running SQL, slow transactions, thread stacks waiting for connections, and connections that are not being returned. I'd also check whether a deployment increased replica count or concurrency, which could multiply total database connections. I wouldn't blindly increase the pool size; I'd fix leaks or long transactions, introduce sensible timeouts, and tune the application's concurrency against the database's real capacity.

WHAT TO CHECK / EXPLAIN:
  • Inspect active/idle/pending/max connections and acquisition timeout trends.
  • Correlate active connections with transaction duration, lock waits, slow SQL, and thread dumps.
  • Check total connections across ALL app replicas; pool x replicas must fit DB limits.
YOUR RESUME CONNECTION

Lowe's: PostgreSQL-backed store-edge services; discuss as your troubleshooting method unless you saw this exact issue.

FOLLOW-UP Could @Transactional cause exhaustion?
Yes, transactions that include slow network calls or excessive work retain connections longer.
Q48
05 • 15 Production Scenarios Concurrency and idempotency

Two users update the same record simultaneously. How do you handle it?

Suggested Spoken Answer (45–60s)

I would prevent lost updates according to the business rule. For typical user-driven changes, I'd use optimistic locking with JPA @Version and return a conflict if someone has already updated the record. The client can reload the latest state and retry deliberately. For highly contended inventory or balance changes, I'd evaluate atomic conditional SQL updates or short database row locks. I'd keep transactions focused and test concurrent requests. A Java synchronized block isn't sufficient when multiple microservice instances are running.

WHAT TO CHECK / EXPLAIN:
  • Optimistic: @Version and OptimisticLockException; return 409 Conflict or equivalent.
  • High contention: UPDATE ... WHERE version/quantity condition or SELECT ... FOR UPDATE inside a transaction.
  • Choose behavior explicitly: reject, merge, retry, or serialize based on domain semantics.
YOUR RESUME CONNECTION

Lowe's: store/inventory services provide a relevant setting; do not claim a conflict-handling implementation you have not used.

FOLLOW-UP Why not Redis locks by default?
Database atomicity or versioning is typically simpler and more reliable for a single DB record.
Q49
05 • 15 Production Scenarios Concurrency and idempotency

A payment request reaches your API twice. How do you prevent duplicate payments?

Suggested Spoken Answer (45–60s)

I would make payment creation idempotent. The client supplies an idempotency key for the logical payment, and the backend atomically reserves that key using a unique constraint, together with a request fingerprint and durable processing status. Q51
05 • 15 Production Scenarios Resilience and transactions

Your retry mechanism starts increasing traffic instead of reducing failures. Why?

Suggested Spoken Answer (45–60s)

That usually means retries are amplifying load on an already unhealthy dependency, possibly with retries at several layers. I would inspect retry counts, response codes, concurrent request volume, and whether clients are retrying at the same time. I'd centralize retry policy at one appropriate boundary, cap attempts, use exponential backoff with jitter, and enforce an overall time budget. I'd combine this with circuit breaking, load shedding, and idempotency for side-effecting operations. The goal is to reduce pressure while the dependency recovers.

WHAT TO CHECK / EXPLAIN:
  • Look for nested retries: three attempts at each of three layers can create up to 27 downstream attempts.
  • Use bounded attempts, jitter, retry budgets, circuit breakers, and explicit retryable error classes.
  • Monitor retry rate, attempts/request, downstream QPS, latency, and successful recoveries.

FOLLOW-UP Why add jitter?

Suggested Spoken Answer (45–60s)

I'd compare incoming message rate with successful processing throughput, then check lag per partition, not just the total. WHAT TO CHECK / EXPLAIN:

  • Identify bottlenecks: slow handlers, SQL, external APIs, large batches, GC, and poison messages.
  • Scale within partition limits; tune poll/batch/commit carefully and consider DLQ or retries with ordering awareness.

One microservice goes down during an order transaction. How should your system behave?

Suggested Spoken Answer (45–60s)

I would design the transaction around explicit business states instead of assuming one distributed ACID transaction across services. For a multi-step order workflow, a saga can coordinate local transactions and compensating actions. I'd use durable events and an outbox pattern to avoid losing state changes, and make each step idempotent. If a downstream service is unavailable, the order should move to a well-defined pending, failed, or compensating state. I'd provide recovery, retries where safe, observability, and reconciliation rather than silently claiming success.

WHAT TO CHECK / EXPLAIN:
  • Use local transactions with a saga (orchestration/choreography) and business-specific compensations.
  • Persist state changes plus outgoing events atomically via transactional outbox when appropriate.
  • Design idempotent handlers, eventual consistency, and a recoverable order state machine.

Q56
05 • 15 Production Scenarios Resilience and transactions

A scheduled job executes twice after deployment. How would you prevent duplicate execution?

Suggested Spoken Answer (45–60s)

I'd check whether multiple instances are running the same @Scheduled job after horizontal scaling or during a rolling deployment. A local synchronized lock won't coordinate multiple pods. Depending on requirements, I'd use a persistent distributed scheduler or a lease-based lock such as a properly configured database-backed scheduler. More importantly, I'd make the job idempotent using a unique run or business-operation key so a restart or expired lock cannot duplicate its effects. I'd track ownership, lock expiry, execution status, and job success metrics.

WHAT TO CHECK / EXPLAIN:
  • Check multiple pods, duplicate scheduler registration, rolling overlap, clock and cron configuration.
  • Use Quartz clustered mode, ShedLock with shared storage, or an equivalent lease/fencing arrangement.
  • Use unique run IDs and durable idempotency because locks alone do not guarantee exactly-once effects.

Your service receives duplicate requests during a network timeout. How would you make the operation safe?

Suggested Spoken Answer (45–60s)

I would assume a timeout means the result is unknown, not necessarily that the operation failed. For operations with side effects, I'd require a stable idempotency key or business request ID and atomically enforce uniqueness in durable storage. Repeated requests should return the previous outcome or a processing status rather than repeat the operation. I'd validate payload consistency for reused keys, define retention and reconciliation policies, and keep event consumers idempotent as well. GET and naturally idempotent updates can use normal HTTP semantics, while create or charge workflows need stronger protection.

WHAT TO CHECK / EXPLAIN:
  • Use a stable client request ID; durable unique constraint and stored result/status for side-effecting writes.
  • Handle in-flight duplicates as PENDING; distinguish transport timeout from business failure.
  • Test concurrent retries across replicas, crash recovery, and message redelivery.
