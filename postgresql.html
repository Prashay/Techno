PART 1: CORE & FOUNDATIONAL QUESTIONS

PostgreSQL Fundamentals Basic • Developer

Object-relational features, JSONB vs JSON, Views, and Foreign Keys.

1. Why is PostgreSQL the premier relational database for modern architectures?

PostgreSQL is an open-source object-relational database renowned for strict SQL standards compliance, rich extensibility, rock-solid ACID guarantees, native JSONB support, and an ecosystem of powerful extensions (e.g. PostGIS, pgvector for AI embeddings, TimescaleDB).

2. Native JSONB vs JSON in PostgreSQL

JSON stores exact text (preserves whitespace and duplicate keys), requiring re-parsing on every query. JSONB decomposes JSON into a binary decomposed format: slightly slower on insert, but dramatically faster on reads and supports GIN indexing for fast sub-property search.

3. Views vs Materialized Views

A standard VIEW is a stored query executed dynamically on every call. A MATERIALIZED VIEW persists the query results physically on disk, offering instant reads for complex aggregations. Refreshed via REFRESH MATERIALIZED VIEW CONCURRENTLY.

PART 2: ADVANCED & 2026 INTERVIEW SPECS

Advanced PostgreSQL Architecture (2026) Senior • Tech Lead • 2026

MVCC dead tuples, index taxonomy (GIN, BRIN, pgvector), and connection pool scaling with PgBouncer.

Storage Internals • MVCC

1. PostgreSQL MVCC, Dead Tuples, and Autovacuum Tuning.

In PostgreSQL, when a row is updated, it does NOT overwrite the old row in place. It marks the old row as a dead tuple (using xmin / xmax transaction IDs) and inserts a new row version:

  • VACUUM: Reclaims disk space occupied by dead tuples so future inserts can reuse those pages.
  • Table Bloat: If Autovacuum runs too slowly on high-write tables, dead tuples accumulate, causing severe table and index bloat.
  • Transaction ID Wraparound: PostgreSQL transaction IDs are 32-bit integers. If not frozen by autovacuum before 2 billion transactions, the database enters emergency read-only mode to prevent catastrophic data loss!

Connection Pooling • Scaling

3. Scaling Connection Limits: Why PostgreSQL requires PgBouncer.

PostgreSQL allocates a dedicated OS process (forking ~5MB to 10MB memory) per connected client. Exceeding 300-500 connections degrades performance due to CPU process context switching and lock contention. PgBouncer acts as a lightweight connection proxy in transaction pooling mode, enabling 10,000 application threads to share 50 backend PostgreSQL connections.
